## Problem and root cause

The shared user store excludes null, although expiration, failed restoration and all logout handlers already store null. SessionUser omits successful-response token fields and nullable status/profile metadata. Strict checks therefore reject existing transitions and status consumers. This repair contributes to G14 / plan13.11 and does not close the full onboarding/retention goal.

## Traced flow and scope

Auth router SessionUserResponse inherits Token and UserProfileImageResponse; SessionUserInfoResponse adds UserStatus plus bio/gender/date_of_birth. Successful serialized token and profile-image fields are strings. Status and extra profile fields are nullable, and date values serialize as strings. Existing base profile snapshots retain optional enrichment fields. Permissions are generated by get_permissions for the valid response.

Session restoration feeds the store from the auth route, VK widget, root layout, Account, UserMenu and message inputs. Expiration/root restoration, app-layout logout and menu logout store null. Initial state remains undefined. Messages infers its user prop from this store; Message receives it unchanged. No handler or default changes.

Tooltip currently accepts string in its declaration but its guard already permits null/undefined input at runtime. Widen only that declaration. In the sanitization branch, elementId is falsy and the enclosing content || elementId guard requires truthy content; the existing logic thus proves content is a string. An erased non-null assertion expresses this existing invariant without changing sanitization or control flow. All Tooltip consumers will be checked by the full strict diagnostic comparison.
