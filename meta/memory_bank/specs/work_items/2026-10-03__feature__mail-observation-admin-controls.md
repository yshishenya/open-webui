# AIRIS — административное управление диагностическими почтовыми группами

Тип: новая функция. Статус: принят на production 04.10.2026. Ветка: codex/feature/mail-observation-admin. Основа: airis_b2c после PR205/206. Процесс: new_feature с проверкой по code_review. SDD Spec: meta/sdd/specs/completed/airis-mail-observation-admin-2026-10-03-001.json.

## Конечный результат этого блока

Администратор через продукт объявляет фиксированную диагностическую группу, запускает полный ограниченный проход, видит ход и ошибки, продолжает после прерывания и закрывает группу. Чужой или анонимный запрос не получает доступа. Повтор HTTP-запроса не создаёт вторую группу, не пропускает страницу и не останавливает корректный проход. Все разрешения рассылки сохраняются выключенными; диагностика не считается добровольным пилотом.

Принятый обработчик и журнал повторно используются; нулевая готовность старой базы не исправляется автоматическим согласием или подтверждением адресов. Связь с очередью, знаменатели рассылки и настоящий пилот требуют отдельной приёмки.

## Требования и проверяемые критерии

### Объявление группы

- [x] Все новые маршруты защищены get_admin_user. Проверены анонимный доступ, обычный пользователь и администратор для каждого действия.
- [x] Новый интерфейс явно обозначает группу как диагностику. Не предлагает запуск добровольного пилота или включение SMTP в этом блоке.
- [x] Регистрационные границы и список участников обязательны. Участники существуют, имеют обычную роль и лежат внутри указанного регистрационного окна.
- [x] Состав включает и людей без согласия/подходящего адреса; не использовать account_candidates и не отбрасывать отрицательных участников молча.
- [x] Верхняя регистрационная граница не позже фактического момента объявления. Платёжное окно может быть будущим; наблюдение читает только реально созданные к текущему моменту платежи.
- [x] Ограничить создание через HTTP до500участников; повторные/пустые/слишком длинные/чужие/несуществующие идентификаторы отклоняются целиком.
- [x] Повтор создания с тем же ключом и тем же содержимым возвращает ту же группу; тот же ключ с другим содержимым даёт409. Решить хранение ключа и отпечатка запроса до реализации; не применять память процесса.
- [x] Назначение группы неизменяемо. Группа observe никогда автоматически не становится dispatch-когортой. Не менять прежнюю закрытую диагностическую группу PR205.

### Проходы, конкуренция и остановка

- [x] Один HTTP-вызов обрабатывает не больше25участников и имеет ограниченный срок выполнения. UI выполняет последовательные страницы и показывает фактический прогресс.
- [x] Первый запуск устанавливает фактическое observed_from; HTTP не принимает тестовый now или дату прошлой проверки.
- [x] Чужая живая аренда возвращает понятное busy-состояние. После истечения аренды возобновляется прежний курсор, без новой записи первого наблюдения.
- [x] Одинаковая аренда может попасть в два HTTP-запроса. Заблокировать строку прохода до чтения его страницы; принимать expected_cursor. Устаревший повтор возвращает409/текущее состояние без записи страницы и без fail_observation_run.
- [x] Возобновление после потери HTTP-ответа не пропускает страницу; результат определяется сохранённым курсором. Не выдавать claim_id в общих GET-ответах и журналах.
- [x] Потерявший аренду запрос не пишет страницу и не останавливает нового владельца. Проверить два разных владельца и два запроса одного владельца на PostgreSQL.
- [x] Пределы100текущих платежей/256сохранённых сценариев и timeout30секунд сохраняются. Ни превышение, ни ошибка не дают completed.
- [x] Закрытие группы сохраняет историю, останавливает незавершённый проход с operator_stop и запрещает новые проходы. Закрытие и новая страница согласованы транзакциями, повтор закрытия безопасен.
- [x] GET ничего не меняет. Все операционные ответы имеют Cache-Control:no-store.

### Состояния и интерфейс

- [x] Список групп ограничен и имеет устойчивое постраничное чтение. Ответ не содержит адресов, текста писем, provider payload, токенов и параметров транспорта.
- [x] Видны объявление/начало/закрытие, неизменяемые границы и число участников; последний проход показывает статус, курсор, проверенных участников/сценарии и безопасную причину ошибки.
- [x] Потерянные источники и неполный проход показаны явно. completed означает обход состава, не непрерывную или историческую полноту.
- [x] UI различает загрузку, пустой список, недоступный сервис, busy, завершение, частичный результат и закрытую группу. Двойное нажатие не порождает параллельных страниц.
- [x] Администратор выбирает участников через существующие административные средства; не вводит SQL или секреты. Понятно, что объявление группы не меняет согласия участников.
- [x] Отмена запроса в браузере не объявляется откатом серверной записи: после неопределённого ответа интерфейс перечитывает состояние.
- [x] Учитывать старые группы без новых административных метаданных как legacy/diagnostic; не выдавать их за созданный через интерфейс добровольный пилот.

## Архитектура и открытые решения до кода

Повторно использовать models/email_observation*.py, utils/airis/email_observer.py и общий send_eligibility. Новая логика — в routers/airis/email_observation.py и отдельном административном модуле; UI в fork-owned компоненте Analytics/EmailObservations.svelte и отдельном клиенте API.

Главный найденный риск: принятый внутренний runner предполагает последовательные вызовы одного владельца. HTTP может повторить запрос параллельно. До экспонирования runner необходимы блокировка строки до чтения страницы и проверка ожидаемого курсора; конфликт не должен проваливать корректный проход. Тестами подтвердить оба варианта конкуренции.

Для идемпотентного объявления группы нужен долговечный ключ плюс отпечаток нормализованного содержания, связанный с администратором. Не использовать пользовательский ключ как scope.id без проверки содержания. Сначала сравнить добавочные метаданные в отдельной fork-owned таблице с новыми nullable-полями группы; выбрать минимальную миграцию, сохраняющую старую диагностику. Не менять семантику immutable membership или observed_from.

Upstream impact: ожидается только тонкое подключение нового маршрута в backend/open_webui/main.py и вкладки в существующей административной аналитике. Не форматировать эти файлы целиком. Основной код/компоненты/тесты новые или принадлежат AIRIS.

После этого блока: атомарная связь положительного решения с новой задачей очереди, отчёт по явно выбранной dispatch-группе с полнотой и настоящий добровольный пилот24h/72h/14d. Эти результаты не симулировать административной диагностикой.

## Решения реализации — 03.10.2026

- Страница захватывает блокировки в порядке scope → run до чтения участников и источников. Используются неизменяющие значение UPDATE только таблиц журнала: PostgreSQL удерживает блокировку строки, SQLite — транзакцию записи. Закрытие и получение аренды используют тот же порядок. Конфликт closed/lost/stale не вызывает fail_observation_run; запись реальной ошибки дополнительно сверяет ожидаемый курсор, чтобы поздний обработчик ошибки не остановил уже сохранённую следующую страницу.
- Для объявления выбираются отдельные административные метаданные с неизменяемыми actor_id, request_key, request_hash и ссылкой на scope. Прежняя схема групп и её история сохраняются. Создание scope + состава + метаданных выполняется одной транзакцией; проигравшее конкурентное создание откатывается к savepoint и читает принятый результат. Ключ привязан к администратору, отпечаток включает отсортированный состав и все границы; повтор после удаления участника возвращает прежний результат.
- Запуск прохода также получает долговечную запись команды (actor/key/hash, scope/run/claim). Повтор принятого запуска не создаёт новый проход после завершения. Новый запуск/перехват требует expected_run_id текущего последнего прохода. Общие GET никогда не возвращают claim_id; отдельный ответ принятого запуска показывает его только автору команды. После истечения/потери аренды повтор старой команды показывает состояние, новую аренду получает отдельная команда.
- Версии из lock/requirements важнее устаревшей сводки tech_stack: FastAPI0.136.3, SQLAlchemy2.0.50, Pydantic2.13.4, Alembic1.18.4. Официальные материалы получены напрямую и сохранены в private-artifacts/airis-mail-observation-admin-20261003: FastAPI dependencies/release0.136.3, SQLAlchemy2.0 DML/changelog и Pydantic2.13.4 models. PyPI подтверждает последние FastAPI0.142.2, SQLAlchemy2.1.3, Pydantic2.13.5, Alembic1.20.0; версии существующего runtime сохраняются ради совместимости всего fork/образа, новых зависимостей нет. Обновление требует отдельного work item, lock/образа, полного backend/frontend и проверки миграций/денег, а не подмены в этом блоке.
