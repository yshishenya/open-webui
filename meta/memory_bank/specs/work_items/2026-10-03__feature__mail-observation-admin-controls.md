# AIRIS — административное управление диагностическими почтовыми группами

Тип: новая функция. Статус: проектирование. Ветка: codex/feature/mail-observation-admin. Основа: airis_b2c после PR205/206. Процесс: new_feature с проверкой по code_review. SDD Spec: meta/sdd/specs/active/airis-mail-observation-admin-2026-10-03-001.json.

## Конечный результат этого блока

Администратор через продукт объявляет фиксированную диагностическую группу, запускает полный ограниченный проход, видит ход и ошибки, продолжает после прерывания и закрывает группу. Чужой или анонимный запрос не получает доступа. Повтор HTTP-запроса не создаёт вторую группу, не пропускает страницу и не останавливает корректный проход. Все разрешения рассылки сохраняются выключенными; диагностика не считается добровольным пилотом.

Принятый обработчик и журнал повторно используются; нулевая готовность старой базы не исправляется автоматическим согласием или подтверждением адресов. Связь с очередью, знаменатели рассылки и настоящий пилот требуют отдельной приёмки.

## Требования и проверяемые критерии

### Объявление группы

- [ ] Все новые маршруты защищены get_admin_user. Проверены анонимный доступ, обычный пользователь и администратор для каждого действия.
- [ ] Новый интерфейс явно обозначает группу как диагностику. Не предлагает запуск добровольного пилота или включение SMTP в этом блоке.
- [ ] Регистрационные границы и список участников обязательны. Участники существуют, имеют обычную роль и лежат внутри указанного регистрационного окна.
- [ ] Состав включает и людей без согласия/подходящего адреса; не использовать account_candidates и не отбрасывать отрицательных участников молча.
- [ ] Верхняя регистрационная граница не позже фактического момента объявления. Платёжное окно может быть будущим; наблюдение читает только реально созданные к текущему моменту платежи.
- [ ] Ограничить создание через HTTP до500участников; повторные/пустые/слишком длинные/чужие/несуществующие идентификаторы отклоняются целиком.
- [ ] Повтор создания с тем же ключом и тем же содержимым возвращает ту же группу; тот же ключ с другим содержимым даёт409. Решить хранение ключа и отпечатка запроса до реализации; не применять память процесса.
- [ ] Назначение группы неизменяемо. Группа observe никогда автоматически не становится dispatch-когортой. Не менять прежнюю закрытую диагностическую группу PR205.

### Проходы, конкуренция и остановка

- [ ] Один HTTP-вызов обрабатывает не больше25участников и имеет ограниченный срок выполнения. UI выполняет последовательные страницы и показывает фактический прогресс.
- [ ] Первый запуск устанавливает фактическое observed_from; HTTP не принимает тестовый now или дату прошлой проверки.
- [ ] Чужая живая аренда возвращает понятное busy-состояние. После истечения аренды возобновляется прежний курсор, без новой записи первого наблюдения.
- [ ] Одинаковая аренда может попасть в два HTTP-запроса. Заблокировать строку прохода до чтения его страницы; принимать expected_cursor. Устаревший повтор возвращает409/текущее состояние без записи страницы и без fail_observation_run.
- [ ] Возобновление после потери HTTP-ответа не пропускает страницу; результат определяется сохранённым курсором. Не выдавать claim_id в общих GET-ответах и журналах.
- [ ] Потерявший аренду запрос не пишет страницу и не останавливает нового владельца. Проверить два разных владельца и два запроса одного владельца на PostgreSQL.
- [ ] Пределы100текущих платежей/256сохранённых сценариев и timeout30секунд сохраняются. Ни превышение, ни ошибка не дают completed.
- [ ] Закрытие группы сохраняет историю, останавливает незавершённый проход с operator_stop и запрещает новые проходы. Закрытие и новая страница согласованы транзакциями, повтор закрытия безопасен.
- [ ] GET ничего не меняет. Все операционные ответы имеют Cache-Control:no-store.

### Состояния и интерфейс

- [ ] Список групп ограничен и имеет устойчивое постраничное чтение. Ответ не содержит адресов, текста писем, provider payload, токенов и параметров транспорта.
- [ ] Видны объявление/начало/закрытие, неизменяемые границы и число участников; последний проход показывает статус, курсор, проверенных участников/сценарии и безопасную причину ошибки.
- [ ] Потерянные источники и неполный проход показаны явно. completed означает обход состава, не непрерывную или историческую полноту.
- [ ] UI различает загрузку, пустой список, недоступный сервис, busy, завершение, частичный результат и закрытую группу. Двойное нажатие не порождает параллельных страниц.
- [ ] Администратор выбирает участников через существующие административные средства; не вводит SQL или секреты. Понятно, что объявление группы не меняет согласия участников.
- [ ] Отмена запроса в браузере не объявляется откатом серверной записи: после неопределённого ответа интерфейс перечитывает состояние.
- [ ] Учитывать старые группы без новых административных метаданных как legacy/diagnostic; не выдавать их за созданный через интерфейс добровольный пилот.

### Изоляция и проверка

- [ ] 0изменений Payment/LedgerEntry/EmailDelivery/EmailPreference/Auth/User,0SMTP/enqueue при каждом административном действии. Аудит оператора может писать только свой разрешённый журнал.
- [ ] Ошибки и журнал сервера не раскрывают адрес, ключ аренды или текст исключения. Нет нового блокирующего ввода-вывода в обработчиках.
- [ ] Проверки миграции/повторного применения/отката нужны, если ключ создания или административные метаданные требуют новой схемы; существующая история сохраняется.
- [ ] SQLite и PostgreSQL: создание/повтор/разные содержимые, права, границы, закрытие, одинаковый владелец/курсор, потеря ответа, новый владелец, отказ/timeout и денежная изоляция.
- [ ] Проверки интерфейса покрывают вызовы/повторы/пустые/ошибочные состояния и прекращение обхода. Общий накопленный долг G14 не считать закрытым чистотой новых файлов.
- [ ] Полный backend, проверки изменённых файлов, точный source SHA и все запущенные CI пройдены. Новые зависимости не добавляются; версии имеющегося образа и официальная документация проверяются до кода.
- [ ] Рабочий выпуск проверяет права и состояние прежней закрытой диагностики через API, сохраняет историю870сценариев/870переходов, все деньги/очередь/настройки и соседние службы.
- [ ] Реальная административная проверка выполняется только в явно диагностической группе; не включать рассылку или менять согласие. Определить обратимый пример до операций на рабочем сервере.
- [ ] Инструкция администратора и остановки/отката, доказательства и SDD завершены. Общая цель не закрывается этим блоком.

## Архитектура и открытые решения до кода

Повторно использовать models/email_observation*.py, utils/airis/email_observer.py и общий send_eligibility. Новая логика — в routers/airis/email_observation.py и отдельном административном модуле; UI в fork-owned компоненте Analytics/EmailObservations.svelte и отдельном клиенте API.

Главный найденный риск: принятый внутренний runner предполагает последовательные вызовы одного владельца. HTTP может повторить запрос параллельно. До экспонирования runner необходимы блокировка строки до чтения страницы и проверка ожидаемого курсора; конфликт не должен проваливать корректный проход. Тестами подтвердить оба варианта конкуренции.

Для идемпотентного объявления группы нужен долговечный ключ плюс отпечаток нормализованного содержания, связанный с администратором. Не использовать пользовательский ключ как scope.id без проверки содержания. Сначала сравнить добавочные метаданные в отдельной fork-owned таблице с новыми nullable-полями группы; выбрать минимальную миграцию, сохраняющую старую диагностику. Не менять семантику immutable membership или observed_from.

Upstream impact: ожидается только тонкое подключение нового маршрута в backend/open_webui/main.py и вкладки в существующей административной аналитике. Не форматировать эти файлы целиком. Основной код/компоненты/тесты новые или принадлежат AIRIS.

После этого блока: атомарная связь положительного решения с новой задачей очереди, отчёт по явно выбранной dispatch-группе с полнотой и настоящий добровольный пилот24h/72h/14d. Эти результаты не симулировать административной диагностикой.
