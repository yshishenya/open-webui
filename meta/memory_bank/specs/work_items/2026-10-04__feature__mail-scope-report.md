## Финальный результат и измеримые критерии

Администратор читает агрегированный отчёт по явно выбранной группе. Все шесть типов показывают наблюдаемые положительные решения, задания и исходы; числители и знаменатели относятся к одной группе, версии правила и сценарию. Отсутствие обхода, потеря источника и неполная история не становятся нулями или полной конверсией.

- [x] Шесть строк присутствуют даже без записей; сумма восьми состояний каждой строки равна уникальным связанным заданиям.
- [x] Показаны уникальные наблюдаемые аккаунты и сценарии отдельно. Для писем регистрации сценарий соответствует аккаунту; для двух платёжных писем — внутренней попытке пополнения. Несколько платежей не превращаются в нескольких людей.
- [x] Первое фактически наблюдаемое положительное решение остаётся прежним после отказа, изменения адреса и жалобы. Будущая задача может иметь связь без положительного решения. Очередь не является знаменателем пригодности.
- [x] В числитель доли входят только принятые задания со своей доказанной связью и положительным решением не позже принятия. Старые несвязанные задания и потерянные связи показаны отдельно; они не повышают новую долю.
- [x] Полнота отдельно сообщает завершённый обход, текущий/последний проход, число посещённых участников, потерянные источники и отсутствие обязательного наблюдения. Только полностью проверенный dispatch-набор получает долю по наблюдаемым положительным решениям; при частичном проходе, несовместимом правиле, диагностической группе или потере источника доля null с причиной. Известный нулевой знаменатель также даёт null, с отдельной причиной.
- [x] Новый источник платежа после последнего обхода делает набор неполным до наблюдения обоих его сценариев. Worker-факт не заменяет обход всей группы. Завершённый обход не объявляется непрерывным наблюдением всех временных состояний.
- [x] Счётчики delivery/bounce/complaint учитывают только факты не позже снимка и могут пересекаться со статусами. Полнота внешних доставочных событий и Inbox остаются неизвестными; долю доставки не вычислять.
- [x] Повторное чтение без событий возвращает одинаковые показатели: 0 DML от расчёта, 0 вызовов SMTP/наблюдателя/reconcile, 0 изменений денег/согласий/очереди/истории.
- [x] GET защищён get_admin_user и no-store на успехе/отказе/валидации; anonymous/ordinary получают401/403. Экспорт не содержит адресов, текста, токенов, идентификаторов получателей/платежей или провайдерских ответов. Предел500участников, ограниченные источники/история и20секундный таймаут не позволяют бесконечную выгрузку.
- [x] Ручная контрольная матрица всех шести типов совпадает с расчётом на SQLite/PostgreSQL. Проверены отрицательные/будущие/частичные/утраченные/старые состояния, две попытки одного человека, повтор и конкурентный снимок.
- [ ] Полный backend, стиль, SDD и CI проверены на точном source; точный образ/копия БД/защищённый выпуск и рабочее чтение приняты. Пилот, настоящие календарные окна и полезность остаются самостоятельными критериями.

## Реализация и повторное использование

Контрольная матрица до написания расчёта (числа относятся к каждому проверяемому типу):

| Состояние | Наблюдаемые подходящие аккаунты / сценарии | Связанные задания / accepted | Доля аккаунтов / сценариев |
| --- | --- | --- | --- |
| Один положительный аккаунт, один запрещённый, полный dispatch-обход, первое письмо принято | 1 / 1 | 1 / 1 | 1 / 1 |
| Тот же положительный аккаунт затем отказался, задание suppressed | 1 / 1 | 1 / 0 | 0 / 0 |
| Связана будущая задача; пока нет положительного решения | 0 / 0 | 1 / 0 | null, известный ноль |
| Две подтверждённые попытки одного человека, обе приняты | 1 / 2 | 2 / 2 | 1 / 1 |
| Из предыдущих двух попыток принята одна | 1 / 2 | 2 / 1 | 1 / 0.5 |
| Есть worker-факт, но проход группы не завершён | Наблюдаемые числа сохраняются | Наблюдаемые числа сохраняются | null, частичный обход |
| Старая accepted-задача без связи, новых подходящих нет | 0 / 0 | 0 / 0; несвязанная1 | null, известный ноль |
| После положительного решения удалена связанная задача | 1 / 1 | 0 / 0; потерянная связь1 | null, потеря источника |
| Закрытая диагностическая observe-группа, даже полный обход | Наблюдаемые числа сохраняются | Наблюдаемые числа сохраняются | null, диагностическая цель |
| После завершения обхода появился новый платёж без двух наблюдений | Прежние факты сохраняются | Прежние факты сохраняются | null, новый ненаблюдаемый источник |
| Несовместимая версия правила / будущая дата факта / неоднозначный последний проход | Фактические счётчики отдельно | Фактические счётчики отдельно | null с конкретной причиной |

Все шесть типов получают отдельную положительную настройку источников и ручные ожидания; конфликтующие регистрационные ветки не искусственно делаются одновременно ready. При одинаковом времени начала двух проходов не выбирать случайный UUID как доказательство последнего полного прохода: неоднозначность должна сохранить null долю. Закрытая группа ограничивает источники моментом закрытия; новые платежи после закрытия не входят в её прошлый набор. Потеря источников после закрытия по-прежнему видна.

Необработанная строка причины из старой очереди не является безопасным текстом для экспорта. Показывать известные служебные коды и общий unknown для остальных; адрес или ответ провайдера в произвольном legacy reason не должен попасть в JSON. Не отдавать scenario_key/payment_id/member_id/delivery_id и реквизиты аренды.

Два небольших fork-owned helper `utils/airis/email_scope_report.py` и `email_scope_report_data.py` читает существующие scope/member/run/scenario/event и EmailDelivery. Использовать имеющиеся определения MailTypeSummary, MailOutcome, MAIL_STATES и причины из mail_outcome_report там, где единицы совместимы. Не менять контракт старого когортного отчёта и его честное null для ненаблюдаемой истории.

Тонкий GET `/{scope_id}/report` в существующем fork-owned router `routers/airis/email_observation.py` возвращает JSON. Повторно использовать административную защиту, no-store и обработку ошибок. GET не объявляет новую группу и не выбирает её автоматически из списка диагностических групп. Новый интерфейс, таблицы, зависимости, процесс и общий центр уведомлений не нужны.

Снимок PostgreSQL использует REPEATABLE READ в отдельной AsyncSession; SQLite получает последовательный согласованный снимок существующей транзакции. Внешнего ввода исторического now нет. Периоды берутся из объявленной группы и фактических времён наблюдения. Наблюдаемые данные не восстанавливают краткие состояния между проходами или утраченную историю. Сравнение источников выполняется только внутри фиксированного набора, с явными пределами.

SQLAlchemy2.0.50 сохраняется по исключению совместимости, уже проверенному для PR210; официальные2.0async/ORMдокументы и текущий2.1.3прочитаны в этой сессии. Обновление зависимости требует отдельного work item и полной проверки денег/runtime. Новых интеграций нет.

## Остановка и откат

Чтение не включает очередь. При ошибке выпуска вернуть сохранённый образ PR210 с текущими настройками; БД и журнал не понижать и не удалять. Не создавать искусственную dispatch-группу на настоящих пользователях ради приёмки. Рабочие диагностические наборы разрешено читать, но их числа не считаются результатами добровольного пилота.
