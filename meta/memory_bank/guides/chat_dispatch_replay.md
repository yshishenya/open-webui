# Защита от повторного запуска генерации

Общий `main.chat_completion` вызывает fork-owned `utils/airis/chat_dispatch.py`
перед прежним обработчиком. Оба HTTP адреса и прежние aliases используют один
вход. Тело прежнего обработчика сохранено.

Для управляемой отправки с `session_id` и намерением создать/изменить чат
`airis_chat_dispatch` хранит уникальное владение `(user_id, operation_id)`.
Явный `operation_id` должен быть UUID. Для старого клиента используются прежние
идентификаторы assistant сообщений через существующий `task_success.operation_id`.
Внутренние и синхронные вызовы сохраняют прежний договор; старое продолжение
ответа без явного UUID также сохраняет прежнее поведение, поскольку оно повторно
использует тот же assistant id для нового намерения.

| Состояние                                | Действие сервера                                                                            |
| ---------------------------------------- | ------------------------------------------------------------------------------------------- |
| Записи нет                               | Уникальная вставка и commit до заголовка, генерации и других внешних действий               |
| Прежний запрос принят                    | Возвращается сохранённое подтверждение с теми же chat/task ids                              |
| Есть владение, подтверждения нет         | 409 `dispatch_pending_or_unknown`; автоматический новый запуск запрещён                     |
| Тот же ключ с другим значимым содержимым | 409 `dispatch_payload_conflict`; побочных действий нет                                      |
| БД недоступна                            | 503 `dispatch_journal_unavailable`; после возможного запуска запись остаётся неопределённой |

Хеш включает всё исходное содержимое, кроме `session_id` и
`metadata.request_id`. Изменение настроек, сообщений или значимых метаданных
не считается тем же запросом. Клиент обязан повторить исходную операцию целиком;
новое намерение, включая новое продолжение ответа, получает новый UUID.

Запись содержит user/operation ids, SHA256 запроса, время и подтверждение
`status`, `chat_id`, `task_ids`. Текст запроса/ответа и учётные данные в ней не
сохраняются. Принятие запроса не записывает завершённый успех и не списывает квоту.
Результат модели, учёт токенов и запись полезного успеха остаются в прежних путях.

Commit перед внешним действием и сохранение подтверждения после действия не
могут составить одну атомарную транзакцию с провайдером. Потерянный процесс или
отказ БД между ними оставляет неопределённое состояние. Его нельзя автоматически
очищать по таймеру и повторять: первая модель уже могла получить запрос.
Принятая запись тоже не доказывает наличие готового ответа после перезапуска.
При восстановлении нужно сверять сохранённые сообщения и состояние задач.

Записи сохраняются для защиты поздних повторов; удаление аккаунта удаляет их
через внешний ключ `ON DELETE CASCADE`. Автоматическая очистка подтверждений
требует отдельного согласованного срока защиты от повторов. Миграция
`d1c020261009` следует за `o1a020261003`; её удаление также удаляет защиту старых
операций, поэтому откат таблицы после рабочего запуска требует отдельного плана.

Общий `tasks.create_task` сначала подтверждает регистрацию Redis, затем
запускает coroutine. Ошибка или отмена регистрации закрывает ещё не запущенную
coroutine и передаёт исходную ошибку вызывающему коду. При неизвестном результате
команды Redis может остаться регистрация без живой задачи; она не разрешает
повторный запуск провайдера. Состояние Redis само по себе не является долговечным
подтверждением выполнения операции.

Проверки: `test/apps/webui/routers/test_chat_dispatch_replay.py` выполняет
настоящие HTTP/JWT/ORM пути; только граница запуска провайдера явно подменена.
`test/util/check_chat_dispatch_postgres.py` отдельно проверяет миграцию,
уникальность между двумя процессами, чтение подтверждения новым процессом и
удаление записей аккаунта на настоящей PostgreSQL. Они не заменяют проверку
реальной модели, списания, восстановления браузера и production выпуска.

## Журнал браузера и восстановление

`utils/airis/chat_dispatch.ts` сохраняет фактическое тело после существующего
`enhanceOpenAIChatCompletionBody` до POST. Область записи: пользователь и chat id
(home для первого обычного сообщения, temporary для временного). Одна
неопределённая операция в области удерживает следующую отправку и очередь.
Начальная запись защищена native Web Locks; при отсутствии Locks или отказе
Storage отправка останавливается, исходный текст остаётся.

Обычная операция использует localStorage и переживает перезагрузку и повторный
вход. Временная использует sessionStorage, ограничена вкладкой и очищается
штатным logout. Для обычного чата сохраняются сообщения текущей операции;
источником результата служит серверный чат. Фактическое тело запроса остаётся
полным. Если оно само превышает лимит Storage, отправка безопасно отказывается;
молчаливое усечение контекста запрещено. Временный чат сохраняет свою историю.

`session_id` не записывается. Прямые `tool_servers` могут содержать ключи;
вместо них сохраняются SHA256 настроек, при повторе подбираются точно те же
текущие настройки. Изменившееся подключение запрещает повтор исходного запроса.
Явно названные поля authorization/api_key/token/password/secret в оставшемся
теле или истории запрещают сохранение. Это проверка структурированных полей,
а не обещание распознавать произвольный секрет в пользовательском тексте.

| GET /api/v1/chat/dispatches/{UUID}         | Поведение браузера                                                         |
| ------------------------------------------ | -------------------------------------------------------------------------- |
| absent                                     | Повтор только по явному действию, с прежними UUID, message ids и телом     |
| unknown или отказ чтения                   | Запись сохранена, POST не выполняется                                      |
| accepted для обычного чата                 | Чтение сохранённой history и текущих задач, POST не выполняется            |
| accepted без готового ответа и живых задач | Запись удерживается, показано обращение в поддержку                        |
| accepted для временного чата               | Повтор запрещён; восстановление потерянного результата пока не реализовано |

GET использует настоящую авторизацию, не имеет побочных действий и запрещает
кэширование. Чужая операция выглядит как absent. Отказ SQLAlchemy даёт безопасный
503; журнал содержит user id и тип ошибки без содержимого запроса.

После восстановления принятой операции убираются только сохранённые queueIds;
добавленные позже элементы остаются. Поле ввода очищается только при точном
совпадении с исходным текстом и вложениями и прежнем экземпляре ввода. Новый
черновик сохраняется. Actor/token/history/scope сверяются после асинхронных
границ; результат старого аккаунта не меняет новый чат.

Открытые границы: извлечение временного ответа после потери событий,
восстановление незавершённого черновика заметки после перезагрузки, полная
приёмка через реальный провайдер и биллинг. Запись принятия и браузерный harness
не закрывают эти границы.

## Создание скрытого чата заметки

У Notes есть два входа создания: POST создаёт новую переписку по намерению,
GET открывает последнюю или создаёт первую. Оба передают создание в
`utils/airis/note_chat.py`, используя существующий primary key `chat.id`.
UUID5 от user/note/operation связывает повтор с прежним чатом. Никаких новых
таблиц и миграций нет. Legacy POST без operation_id сохраняет создание новой
переписки; первое GET создание использует стабильное намерение UUID(int=0).

Первичный ключ защищает два одновременных запроса. После IntegrityError
транзакция откатывается, затем читается победившая запись. Повтор допустим
только для того же владельца и метаданных internal/type/note_id. Другой чат с
таким ключом получает 409, оставаясь без изменений. Отказ SQLAlchemy даёт 503
без деталей подключения. Повтор создания не сбрасывает title/history/params
прежнего чата и не запускает модель. После намеренного удаления чата повтор
может создать пустую запись с тем же id; долговечный dispatch journal продолжает
защищать прежние операции модели.

Браузер сохраняет UUID под user/note до открытия нового пустого черновика,
используя native Web Locks. После потерянного HTTP ответа onCreateEmbeddedChat
повторяет тот же UUID. Запись содержит только UUID, без текста/ключей. Удаление
локальной записи допустимо только после подтверждённого ответа с владельцем и
note_id; ошибка очистки не превращает принятое создание в отказ. Actor, token,
note id и draft UUID сверяются после ожиданий: поздний ответ не открывает
чужую текущую заметку и не заменяет новый черновик.

Эта защита создания не является доказательством восстановления текста
незавершённого черновика после перезагрузки. Сохранение и восстановление текста
до запуска модели требуют отдельной проверки существующего saveDraft пути.
