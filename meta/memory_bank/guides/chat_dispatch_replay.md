# Защита от повторного запуска генерации

Общий `main.chat_completion` вызывает fork-owned `utils/airis/chat_dispatch.py`
перед прежним обработчиком. Оба HTTP адреса и прежние aliases используют один
вход. Тело прежнего обработчика сохранено.

Для управляемой отправки с `session_id` и намерением создать/изменить чат
`airis_chat_dispatch` хранит уникальное владение `(user_id, operation_id)`.
Явный `operation_id` должен быть UUID. Для старого клиента используются прежние
идентификаторы assistant сообщений через существующий `task_success.operation_id`.
Внутренние и синхронные вызовы сохраняют прежний договор; старое продолжение
ответа без явного UUID также сохраняет прежнее поведение, поскольку оно повторно
использует тот же assistant id для нового намерения.

| Состояние                                | Действие сервера                                                                            |
| ---------------------------------------- | ------------------------------------------------------------------------------------------- |
| Записи нет                               | Уникальная вставка и commit до заголовка, генерации и других внешних действий               |
| Прежний запрос принят                    | Возвращается сохранённое подтверждение с теми же chat/task ids                              |
| Есть владение, подтверждения нет         | 409 `dispatch_pending_or_unknown`; автоматический новый запуск запрещён                     |
| Тот же ключ с другим значимым содержимым | 409 `dispatch_payload_conflict`; побочных действий нет                                      |
| БД недоступна                            | 503 `dispatch_journal_unavailable`; после возможного запуска запись остаётся неопределённой |

Хеш включает всё исходное содержимое, кроме `session_id` и
`metadata.request_id`. Изменение настроек, сообщений или значимых метаданных
не считается тем же запросом. Клиент обязан повторить исходную операцию целиком;
новое намерение, включая новое продолжение ответа, получает новый UUID.

Запись содержит user/operation ids, SHA256 запроса, время и подтверждение
`status`, `chat_id`, `task_ids`. Текст запроса/ответа и учётные данные в ней не
сохраняются. Принятие запроса не записывает завершённый успех и не списывает квоту.
Результат модели, учёт токенов и запись полезного успеха остаются в прежних путях.

Commit перед внешним действием и сохранение подтверждения после действия не
могут составить одну атомарную транзакцию с провайдером. Потерянный процесс или
отказ БД между ними оставляет неопределённое состояние. Его нельзя автоматически
очищать по таймеру и повторять: первая модель уже могла получить запрос.
Принятая запись тоже не доказывает наличие готового ответа после перезапуска.
При восстановлении нужно сверять сохранённые сообщения и состояние задач.

Записи сохраняются для защиты поздних повторов; удаление аккаунта удаляет их
через внешний ключ `ON DELETE CASCADE`. Автоматическая очистка подтверждений
требует отдельного согласованного срока защиты от повторов. Миграция
`d1c020261009` следует за `o1a020261003`; её удаление также удаляет защиту старых
операций, поэтому откат таблицы после рабочего запуска требует отдельного плана.

Общий `tasks.create_task` сначала подтверждает регистрацию Redis, затем
запускает coroutine. Ошибка или отмена регистрации закрывает ещё не запущенную
coroutine и передаёт исходную ошибку вызывающему коду. При неизвестном результате
команды Redis может остаться регистрация без живой задачи; она не разрешает
повторный запуск провайдера. Состояние Redis само по себе не является долговечным
подтверждением выполнения операции.

Проверки: `test/apps/webui/routers/test_chat_dispatch_replay.py` выполняет
настоящие HTTP/JWT/ORM пути; только граница запуска провайдера явно подменена.
`test/util/check_chat_dispatch_postgres.py` отдельно проверяет миграцию,
уникальность между двумя процессами, чтение подтверждения новым процессом и
удаление записей аккаунта на настоящей PostgreSQL. Они не заменяют проверку
реальной модели, списания, восстановления браузера и production выпуска.
