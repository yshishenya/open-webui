подтверждения владельцем и не заменяет live проверку.

## Продукт: ID задаётся при сборке

`svelte.config.js` использует `adapter-static`. Несмотря на импорт
`$env/dynamic/public`, значения публикуются в статическом `build/_app/env.js`.
Установка env только при запуске готового образа или рестарт контейнера не
изменяет frontend. Нужна пересборка и публикация образа.

Для GitHub Actions:

1. В нужном репозитории открыть Settings → Secrets and variables → Actions → Variables.
2. Добавить **repository variable** `PUBLIC_YANDEX_METRICA_ID` с подтверждённым
   номером существующего счётчика. Это публичный measurement ID, не OAuth token.
3. `.github/workflows/docker.yaml` передаёт значение в Docker build args после
   применения исправления этого аудита.
4. Собрать и опубликовать новый образ, затем развернуть по действующему deploy workflow.
5. Проверить публичный `/_app/env.js`: ID заполнен и совпадает с кабинетом.

`PUBLIC_GA_MEASUREMENT_ID` остаётся пустым, пока не требуется Google Analytics.
Идентификаторы не вписывать в исходный код или committed env.

Для этой выкладки пользователь требует сборку только на своём компьютере.
Готовые команды: `meta/docs/releases/metrica-local-build.md`. Сервер выполняет
только pull/import и guarded Docker rollout.

Для локальной сборки Compose принимает переменную через `build.args`, например:

```sh
PUBLIC_YANDEX_METRICA_ID=<подтверждённый_ID> docker compose -f docker-compose.yaml build airis
```

Для `scripts/deploy_prod.sh` передать переменную через окружение или его
`DEPLOY_ENV_FILE` (по умолчанию `.env.deploy`). Обычная `.env` проекта не равна
`.env.deploy`. Публикация/деплой выполняются по принятому процессу релиза.

## Tilda: отдельное подключение

В Tilda: **Настройки сайта → Аналитика → Яндекс Метрика → номер счётчика →
Сохранить → опубликовать все страницы**. Настройка без перепубликации не меняет
опубликованный сайт. После публикации проверить загружаемые scripts и ID в браузере.

Для общей воронки использовать один подтверждённый счётчик на обоих доменах.
В кабинете Метрики проверить основной и дополнительные адреса `airis.you` и
`chat.airis.you`, ограничения адресов и поддоменов. Не включать dev-домен
автоматически: тестовые события загрязняют production статистику.

Tilda и продукт имеют разные origins. `localStorage` согласия продукта не
разделяется с Tilda. На Tilda отдельно проверить управление consent и запуск тега
только после согласия; не считать наличие cookie-баннера доказательством gating.
Для общей идентификации браузера проверить cookie `_ym_uid` на родительском домене
и сохранение первого рекламного источника. Не добавлять внутренние UTM на кнопки
«Открыть продукт»: они могут заменить исходную кампанию.

Источники:
[Подключение в Tilda](https://help-ru.tilda.cc/statistic/yandex-metrika),
[настройки счётчика](https://yandex.ru/support/metrica/ru/general/counter-general),
[cookies Метрики](https://yandex.ru/support/metrica/ru/general/cookie-usage),
[согласие](https://yandex.ru/support/metrica/ru/general/notification).

## SPA, источники и приватность

Общий adapter использует `init` с `defer: true`: автоматический первый просмотр
отключён. `AnalyticsBootstrap` отправляет один `hit` при изменении pathname и при
первом согласии. Anchor/hash-переходы не считаются новыми страницами.

В `hit` передаются путь и только разрешённые campaign query keys:
`utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `gclid`,
`yclid`, `ymclid`. Произвольные query и fragments исключены, заголовки отключены.
Значения рекламных меток ограничены по длине, но не являются свободным полем:
маркетинг не должен помещать в них email, имя, текст запроса или другие личные данные.

UTM должны присутствовать в первом просмотре визита, иначе стандартные отчёты об
источниках их не увидят. Параметры UTM в `reachGoal` не заменяют UTM первого `hit`.
Campaign query сохраняются в памяти через ранние SPA-редиректы до согласия;
после согласия сохраняются в localStorage и входят в первый hit. Реферер
первого просмотра очищается от query/hash, следующие просмотры используют
предыдущий безопасный адрес. Для полной атрибуции ещё нужна live проверка
перехода с внешней Tilda и OAuth. Unit-тест adapter этого не заменяет.

Вебвизор и автоматическое отслеживание внешних ссылок отключены в продукте:
помимо текста сообщений приватные данные могут находиться в sidebar, профиле,
админке и URL файлов. Санитайзер event payload не защищает от записи DOM.
На публичном Tilda-лендинге Вебвизор можно включить отдельно после проверки полей
и consent. Для возврата записи в продукт необходим полный аудит маскировки
`ym-hide-content`, `ym-disable-keys` и `ym-disable-tracklink`.

Источники:
[SPA](https://yandex.ru/support/metrica/ru/code/counter-spa-setup),
[init](https://yandex.ru/support/metrica/ru/code/counter-initialize),
[UTM](https://yandex.ru/support/metrica/ru/general/source-tags),
[hit](https://yandex.ru/support/metrica/ru/objects/hit),
[конфиденциальность](https://yandex.ru/support/metrica/ru/general/confidential-data),
[CSS-маскировка](https://yandex.ru/support/metrica/ru/code/html-markup).

## Цели и доход

Проверить существующие цели прежде, чем создавать новые. Для каждого ID ниже
нужна цель типа JavaScript/«Целевое событие» с точным идентификатором:

| Результат                                  | ID, который уже отправляет продукт |
| ------------------------------------------ | ---------------------------------- |
| Переход с CTA внутренних публичных страниц | `landing_cta_click`                |
| Просмотр формы регистрации                 | `lead_signup_form_viewed`          |
| Начало регистрации                         | `lead_signup_started`              |
| Успешная регистрация                       | `lead_signup_completed`            |
| Первый запрос в текущей browser session    | `activation_first_prompt`          |
| Первый ответ в текущей browser session     | `activation_first_response`        |
| Создание платежа                           | `billing_topup_payment_created`    |
| Подтверждённое пополнение                  | `revenue_topup_completed`          |
| Завершение onboarding                      | `onboarding_completed`             |

Текущие first-prompt/response flags хранятся в `sessionStorage`: это не уникальная
активация пользователя за всё время. Называть такой отчёт lifetime activation
нельзя. OAuth-вход и возврат авторизованного пользователя тоже нужно проверить
отдельно: наличие `signup_completed` для email не доказывает покрытие social signup.

`page_scroll_depth` также отправляется, но сейчас его глубина вычисляется по
document/window. Это полезно для длинных публичных страниц; внутренний scroll
контейнера чата он не измеряет. В Tilda событий из Svelte нет: настроить её
собственные кнопки и формы, затем сопоставить с общими целями. В продукте вызов
`contact_form_submit` не найден; не создавать цель только по историческому списку.

Ecommerce в коде использует `dataLayer.ecommerce.purchase`, `currencyCode`,
`actionField.id/revenue`, статический товар wallet top-up. Проверить включение
ecommerce/dataLayer в кабинете. Доход отправляется после подтверждения зачисления,
не после открытия платёжной формы. Включить удаление повторных покупок между
визитами; текущая client-side дедупликация действует лишь в browser session.
Сверять доход с YooKassa и billing ledger: пользователь может не вернуться после
оплаты, не дать согласие или блокировать счётчик, поэтому frontend отчёт не равен
бухгалтерскому источнику правды. Если нужен полный revenue, отдельным work item
рассмотреть server-side/offline conversions по документации Яндекса.

Составная цель проверяет последовательность внутри одного визита и имеет максимум
10 шагов. Для покупки через несколько дней нужны отдельные конверсии/когорты.

Источники:
[reachGoal](https://yandex.ru/support/metrica/ru/objects/reachgoal),
[составная цель](https://yandex.ru/support/metrica/ru/general/goal-steps),
[ecommerce](https://yandex.ru/support/metrica/ru/ecommerce/data).

## Проверка после публикации

1. Сверить выбранный ID в кабинете, Tilda и product env.js.
2. На тестовом профиле без блокировщиков открыть сайт с `_ym_debug=2`.
3. До согласия provider tag/requests в продукте отсутствуют; после согласия
   появляются `tag.js` и запрос `watch/<ID>` с PageView. Ответ сети сам по себе
   ещё не доказывает включение визита в отчёт: фильтры могут его исключить.
4. Перейти между страницами продукта: один PageView на переход, без hash-дублей,
   токенов, названий чата и пользовательского текста в payload.
5. Проверить цели реальным сценарием, убедиться в точных IDs; не имитировать
   production покупки ради тестирования. Проверить ecommerce в test environment.
6. В кабинете проверить адреса, «Не учитывать мои визиты», IP/URL фильтры,
   фильтрацию роботов, текущий период, часовой пояс и отсутствие случайного сегмента.
7. Подождать обычно 10–15 минут до обычных отчётов; первые ecommerce данные могут
   появляться через несколько часов. Затем сверить визит и цель в отчёте.
8. Проверить отзыв consent и повторное открытие настроек на product страницах.

Источники:
[проверка счётчика](https://yandex.ru/support/metrica/ru/general/check-counter),
[фильтры](https://yandex.ru/support/metrica/ru/general/filters),
[обработка данных](https://yandex.ru/support/metrica/ru/general/how-it-works).

## Дополнительная ошибка Tilda

Браузер и `node --check` выявили синтаксическую ошибку в опубликованном
inline Chatra script. Утрачены операторы `||` в двух выражениях:

```js
// Правильно:
w[c] = w[c] || function () {
  (w[c].q = w[c].q || []).push(arguments);
};
```

В текущем HTML написано `w[c] = w[c] function ()` и `w[c].q = w[c].q []`,
поэтому script не выполняется. Это отдельный дефект виджета Chatra; его нужно
исправить в пользовательском коде Tilda и перепубликовать страницы. Он не
доказывает наличие или отсутствие Метрики — её отсутствие подтверждено отдельно.
