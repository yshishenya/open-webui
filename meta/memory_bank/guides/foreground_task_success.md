# Foreground task success

Specification: `meta/memory_bank/specs/work_items/2026-10-02__feature__foreground-success.md`.

`airis_task_success` is the server source for onboarding activation, task counts and first/last success. It stores authenticated account ID, operation ID, fixed `foreground_chat` kind, completion time and source. It stores no content. Successful completion means a visible nonempty answer or an owned, displayed local artifact with available nonempty bytes. This is a technical result, not a judgement that the task was useful. The checkpoint describes the terminal result delivered before optional outlet/background processing; later edits do not undo an already completed delivery.

The UI creates one operation UUID per explicit generation, shared across model fanout. HTTP replay with the same UUID and repeated completion events keep one record; explicit continuation or regeneration gets a new UUID. Legacy callers use sorted assistant IDs; callers with no IDs get a server UUID and need an explicit operation UUID for request replay idempotency. Duplicate completion retains the earliest confirmed time. Internal agents, timer/automation calls, errors, content-filter failures, declared incomplete responses, reasoning-only output, missing files and interrupted streams do not count. A continuation without changed visible text or a new available artifact does not count its old output again.

Optional client events `first_prompt_submitted` and `first_response_received` are consent-bound lifetime funnel observations, deduplicated and merged by the existing analytics identity service. They are not first-in-tab flags in the current implementation. Their sample omits accounts without analytics consent and does not cover every server completion path. Do not use them to select email recipients or compute an all-account activation denominator. Historical imported assistant messages are only a labelled proxy; the new journal does not backfill them.

Saved normalized responses carry a server-only pending checkpoint list in `chat_message.success_checkpoints`. The persistence method receives a separate keyword; client message JSON and imports cannot create this column. Checkpoints append under a row lock, preserving pending continuation proofs. Journal insertion and checkpoint cleanup commit atomically. The existing scheduler reconciles up to 100 pending messages every five minutes, regardless of the user automation flag; repeated reconciliation is idempotent. Chat deletion leaves committed task counts; account deletion removes them. A process exit after checkpoint commit can be repaired. Before that commit, or during a total database outage for a temporary/API result, no storage mechanism can reconstruct the result from absent content; errors are explicitly logged and must not be counted as a recovered success.

Foreground writes make three bounded async attempts, five seconds each, with short backoff. Exhaustion returns without breaking the answer and logs sanitized error types. Reconciliation has a 15-second deadline and backs off five minutes after a database failure. Alert on exhausted writes or persistent pending checkpoints before enabling scenario email. Do not expose raw checkpoints or journal identities in an ordinary-user report; later cohort reporting uses administrator-only aggregates.

No new environment flag, dependency, process or broker. Product email flags remain off. Before release run SQLite and PostgreSQL regression checks, upgrade/downgrade/reupgrade, full backend/frontend checks and baseline lint/type comparison. A rollback image must understand revision `s1c020261002` while preserving the prior product consent guard and service email.
