# Durable email observation journal

The journal records a declared population and real observations of send eligibility. It contains no message text, address, token or provider response. Rule version: `send_eligibility_v1`. Initial storage release: PR203, migration `o1j020261003`.

## Storage and ownership

- `models/email_observation_schema.py`: five additive tables, foreign keys, constraints and indexes.
- `models/email_observation.py`: async storage primitives. Callers own an independent AsyncSession and the outer commit/rollback. No storage operation enqueues or sends email.
- `utils/airis/email_eligibility.py`: authoritative read-only business decision. Its ready result is separate from release/pilot/dry-run/transport permission.

Use `declare_scope` to freeze ordinary members, including unverified accounts and members without product consent. Declare registration/payment windows explicitly. Duplicate, missing, nonordinary and out-of-window identities are rejected. Canonical account scenario key is onboarding_v1; a payment scenario key equals the internal Payment.id. A deleted source can only update its already-known orphan history.

`claim_observation_run` starts one live run per scope or reclaims an expired lease. It records actual observation start once. Never supply artificial historical time on production. `observation_page` reads up to100members; `save_observation_page` validates owner/lease/sequence and saves decisions/events/cursor/counts within a savepoint. Commit only after the whole page succeeds. A caught page error cannot retain partial journal changes. Interrupted runs retain their cursor; a stale owner cannot write after reclaim. `fail_observation_run` records an incomplete run with a bounded safe reason.

The original scenario window/source identity and first_eligible_at are immutable. Identical decisions add no transition event. Changed reasons/defer times add one new revision. Late opt-out preserves the earlier first-positive fact. Deleted user/payment/job foreign keys become NULL; linked_at retains evidence of a lost delivery link, and a replacement job cannot impersonate it.

## Interpretation and rollout boundary

A completed run proves every declared member was visited. It does not prove continuous observation between passes or that the caller supplied every relevant scenario. Empty tables or no completed runs do not imply zero eligible people.

The storage release creates no scopes and enables no observer or dispatch. Existing administrative reports retain null eligibility denominators until observer, queue association and coverage-aware reporting are separately implemented and accepted. New history cannot reconstruct old unobserved eligibility. Actual SMTP acceptance does not prove external delivery or Inbox placement.

Dispatch integration calculates business eligibility through the shared helper and saves its fact plus a new exact-scenario queue association in one transaction. A future scheduled task can have a receipt before its first actual positive decision. Release/pilot/dry-run/consent/address permissions are still checked immediately before SMTP. Monetary transactions finish separately; journal failure must never undo payment credit. This integration has its own verification/release gate; its existence does not close reporting or pilot acceptance.

## Bounded callable observer

`utils/airis/email_observer.py` exposes `observe_scope_page(scope_id, claim=...)`. Its default and all HTTP calls accept only an open observe scope. The queue's internal caller explicitly selects mode=dispatch for its declared population; this does not enqueue or send mail. A scope can declare an explicit future payment end before prospective payments arrive, while registration membership must already exist. Read payments only up to actual current time. Never expose internal `mode` or `now` test injection through HTTP or use it to backfill production observations.

## Queue association and dispatch facts

`AIRIS_EMAIL_OBSERVATION_SCOPE_ID` defaults empty: no journal queries are added to the legacy enqueue/submit path. A nonempty value requires an open dispatch group with the current rule version. Declare this separate frozen group prospectively using existing internal storage primitives; the administrator HTTP interface remains diagnostic only. Never convert a diagnostic group to dispatch or assume membership is consent. Source boundaries and current permission remain mandatory.

`utils/airis/email_dispatch.py` reuses enqueue_email, send_eligibility and decision/event storage. Acquire the selected scope lock before User/Delivery locks. Scope -> User -> Delivery -> scenario order serializes the queue with observation pages; SQLite RETURNING work is drained on cancellation before session rollback. Only the ID returned for a newly inserted task may receive a new association. A duplicate or old job cannot retroactively gain a receipt; a lost delivery foreign key retains linked_at and cannot be replaced. A scheduled negative fact can link to its exact pending task without setting first_eligible_at. Canonical windows come from original User/Payment creation, not mutable retry/frequency/capacity due_at.

Both prepare_email checks write business decisions for already associated tasks before release flags and transport capacity decide submission. Current queue identity/category/payment/expiry and current source windows must still match. An unassociated task is suppressed with observation_unlinked. Invalid/closed/diagnostic selected groups stop the path without bypass. Business-ready is observed independently of release/dry-run/global transport permission; first_eligible_at never changes after later refusal. Worker decision events have run_id=null and never alter population cursor/counts.

Each scheduler tick visits one bounded dispatch page before reconciliation/draining. Its persisted running lease/cursor survives restarts; after expiry a new tick resumes it. All frozen members are visited, including negative and deleted sources, regardless of queue candidate filters. A partial/failed/source-lost run remains partial/unavailable for later reporting. At the existing five-minute polling interval, 25 members/page means a 500-member traversal takes up to 100 minutes; shorten the interval or partition groups only if actual pilot size requires it. No passage of time or transport acceptance proves useful outcomes or inbox placement.

## Administrative diagnostic controls

The administrator's Analytics panel has an Email diagnostics tab. Declare 1–500 ordinary accounts with explicit registration/payment bounds, including accounts without permission or verified addresses. The registration upper bound cannot be in the future. Payment bounds may include future time; the observer still reads only payments created by actual current time. Creating the group never changes consent, account roles or address verification, money or mail transport permissions. Existing authentication may update the operator last_active_at; this is separate from diagnostic writes.

The API is `/api/v1/admin/email-observations`: GET collection and `/{id}` are read-only; POST collection declares; POST `/{id}/runs` starts/resumes; POST `/{id}/pages` visits at most25members; POST `/{id}/closure` closes with history retained. Every route uses `get_admin_user` and all success/error responses are `Cache-Control: no-store`. Validation errors do not echo request input. Responses contain counts and safe state, never recipient addresses, email bodies, provider payload or transport settings. Generic reads never contain claim credentials.

The additive `o1a020261003` migration creates `airis_email_observation_command`. Actor/key uniqueness and the normalized-content SHA256 make declaration and start commands durable across server restarts. Same actor/key/body returns the same result; changed content gives409. Scope, frozen membership or lease and its receipt commit together. Replaying a completed start cannot create another run. Command receipt sequence resolves runs started within the same second. Actor IDs remain in this content-free audit after account deletion.

A run start requires `request_key` and `expected_run_id` (explicit null before the first run); scope declaration requires `request_key`, `user_ids` and all four source bounds. Page requests require the returned `run_id`, `claim_id` and `expected_cursor`. Credentials are associated with the authenticated actor who started that command. New HTTP input cannot inject `now` or rewrite past observation time.

Before any member/source read, each page locks scope then run. The same order coordinates claiming, page saving and closure. An old cursor, completed/closed group or lost lease produces409 without calling the run failure writer. Actual error recording also compares the expected cursor, so a late timeout handler cannot fail a subsequently saved page. SQLite driver work acquiring a lock is drained before cancellation rolls back its session, avoiding an abandoned RETURNING cursor retaining a write lock.

The browser issues pages sequentially and disables duplicate actions. Stopping waits for the current page to settle; it does not claim server rollback. After an uncertain page response, reread the saved position; after an uncertain declaration, retry the same frozen form/key. A new operator cannot take a live lease; wait until its180second expiry and resume from saved cursor. Closing the group marks its unfinished run `operator_stop` even if the lease expired and preserves all decisions and source-loss evidence. Repeated closure retains its original timestamp. Completed still means population traversal only; older groups are explicitly diagnostic, never inferred volunteer cohorts.

## Scope report

`GET /api/v1/admin/email-observations/{scope_id}/report` reads one explicitly selected scope through the existing administrator guard. Success, authentication errors and validation errors are no-store. The read never runs the observer, reconciliation or transport. The response contains aggregate counts and safe whitelisted codes; no recipient/payment/job/scenario IDs, addresses, message bodies, tokens or provider payloads. Group ID is the explicit selection key.

Each of the six types separates distinct observed positive accounts from scenarios. Registration scenarios use one account; payment scenarios use one internal payment attempt. Only an accepted job with its original matching association and a first positive decision no later than acceptance contributes to the observed numerator. Future acceptance, missing timestamps or mismatched identity invalidate the fraction. Linked pending jobs can exist before any positive decision. Old unlinked jobs and lost links remain separate counts.

`coverage.state=complete_traversal` requires the latest unambiguous completed pass, matching membership, all current bounded sources observed, supported rule and no missing/changed/future sources or links. Failed/running/ambiguous passes, payments arriving after a pass or deleted sources retain partial coverage. Continuous history remains unavailable. Diagnostic scopes never acquire dispatch fractions. Unknown denominators are null with a reason; known zero is denominator0, fractionnull and zero_observed_denominator. Historical legacy cohorts retain their existing unknown eligibility.

Queue states describe the current snapshot; delivery/bounce/complaint events through generated_at can overlap those states. SMTP acceptance does not prove delivery or Inbox. External receipt coverage and delivery fractions remain unknown. Closed scope source reads end at closed_at; queue outcomes are current recorded facts. Retained first-positive decisions are not undone by later refusal.

The two fork-owned report helpers use an independent read transaction: PostgreSQL REPEATABLE READ and a real SQLite transaction started by an ORM savepoint. The read is bounded to500members,100payments/256scenario history per member and20seconds. A cap overflow fails explicitly, never silently truncates a successful report. Tests include actual second-connection commits between source and queue reads on both databases. Use test_email_scope_report.py and test_email_scope_report_edges.py with the existing disposable PostgreSQL fixture; never point it at production.

This report alone does not establish a volunteer pilot, usefulness, causality or mature24h/72h/14d conversion. It does not enable queue/release flags or choose a dispatch scope. Restore the previous image for an application rollback, retaining all sources and journal data; disable dispatch before changing its selector.
